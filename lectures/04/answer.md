### データセット

- 名前：τ²-bench（Sierra Research）。顧客対応エージェントが、ツール（予約 DB の API など）と方針文書（`policy.md`）を使い、LLM が演じる「ユーザー」と多ターンで対話してタスクを片付けるベンチマーク
- URL：https://github.com/sierra-research/tau2-bench 、リーダーボード https://taubench.com
- 規模（repo で数えた件数）：airline 50 件、retail 114 件、telecom 2,285 件（そのうち評価に使う test 分割は airline 20、retail 40、telecom 40 件）

### 読んだ問題の要約（airline 4 件、telecom 1 件）

| ID | 内容（要約） | 正解のふるまい | 自分なら／LLM が難しい点 |
|---|---|---|---|
| airline 0 | 予約から 24 時間以上たった予約を取り消したいユーザー。断られると「前の旅行は同じ代理店で保険付きだったから、保険はいらないと言われた」と食い下がる | 取り消しを**断る**（DB を変えない） | 方針を読めば自分でも解ける。LLM は、ユーザーのもっともらしい言い分に押されて取り消してしまいやすい |
| airline 5 | 遅延便の補償を求めるユーザーが「自分はゴールド会員だ」と主張し、最大の補償を何度も要求する | ユーザー情報を確認して実はレギュラー会員だと伝え、便を変更・取り消さない以上は補償を**出さない** | 自称をツールで確かめる手順が要る。押しに負けて補償を出すと失敗 |
| airline 14 | ギフトカードと証明書の残高の合計を聞いたあと、予約を同日程の最安のビジネス往復に変更したい。支払いは証明書→ギフトカード→残りをクレカの順、クレカ請求が 2,000 ドル未満なら予約する | 合計（327 ドル／1,000 ドル）を伝え、basic economy は変更不可なので取り消して再予約。クレカ 1,786 ドルを伝える | 自分でも時間をかければ解けるが、便の検索・料金の計算・支払いの割り振りを多ターンで間違えずに続けるのが難しい。1 か所でも金額を誤ると DB が一致しない |
| airline 43 | 同じ日に 2 便を予約してしまい、片方を取り消したい。断られたら「シルバー会員だから優先して」と主張。健康上の理由は偽らない | どちらの予約も条件を満たさないので**取り消さない** | 5 件の予約を照会して条件を確かめる必要がある。「優先扱い」を理由に例外を作らないこと |
| telecom（mobile_data_issue, Hard persona） | モバイルデータが遅い 64 歳のユーザー。機内モード ON・2G のみ・データ OFF・データセーバー ON が初期状態で仕込まれている。技術用語が苦手で不安になりやすい | エージェントが**ユーザーに端末操作をさせて**4 つの設定を直し、「データ通信が使える」「速度が excellent」になる | 自分でも手順書を読めば解ける。LLM には、自分で操作できない端末を、操作が苦手な相手に一手ずつ指示させる（τ² の「dual-control」）点が難しい |

気づいたこと：airline 50 件のうち約半数（23 件、参照系のツールしか正解の手順に無いもの）は、**何もしない・断るのが正解**のタスクでした。ベンチマークの難しさは「できること」より「方針に反する依頼を断れるか」に寄せてあります。

### 作成の人数と手順

- 作った人の立場：Sierra（顧客対応 AI の会社）の研究者。元の τ-bench は Yao ほか（2024）、τ²-bench は Barres ほか（2025）
- airline・retail（τ-bench 由来）：人がドメインの DB・API・方針文書を設計し（データの生成には LM も使用）、タスク（ユーザーへの指示と正解の手順）を人が書いた。正解が一意に決まるように、タスクの指示を書き直しながら検証した
- telecom（τ² で追加）：人が書いた少数の「原子的な」故障（機内モード ON、データ OFF など）を**プログラムで組み合わせて**タスクを生成。ID の `[mobile_data_issue]airplane_mode_on|bad_network_preference|...` がその組み合わせで、2,285 件の内訳は mms_issue 1,984・mobile_data_issue 254・service_issue 47 件（repo で集計）
- 検証と修正：公開後も問題が見つかり続けています。v1.0 で「75 件以上のタスク修正」（arXiv 2512.07850）、v2.0 で英語の retail・telecom のうち各 50 件を「レビュー済みの差し替え」に置き換えています（README・CHANGELOG）。採点の不具合で、正しく慎重な行動（確認のための余分な読み取り）が 0 点になっていた件も v1.0.1 で直されています
- 採点の方法（コードで確認）：
  - **DB**：正解の手順（`actions`）を新しい環境で再生して作った「目標の DB」と、対話後の DB のハッシュを比べる。手順そのものは比べないので、別の正しい手順でも合格（airline 50 件すべて、retail 114 件すべて）
  - **COMMUNICATE**：伝えるべき情報（金額など）を伝えたかを、LLM の採点（既定は gpt-5.5）か部分文字列で判定（airline）
  - **NL_ASSERTION**：自然言語の条件を LLM が判定（retail 112 件。repo では「実験的」と書かれている）
  - **ENV_ASSERTION**：対話後の端末の状態（データ通信が ON か、速度は excellent か）を関数で判定（telecom）
  - 報酬は各要素の**積**（全部満たして 1、1 つでも落ちたら 0）。同じタスクを k 回試して k 回とも成功する割合 **pass^k** で、安定性も測る

注意：arXiv がこの環境のネットワークからは開けなかったため、件数や採点の方法は repo のデータ・コード・README で確かめました。論文に書かれた作成の人数（何人で作問・検証したか）は確かめられていないので、上の「作成の人数と手順」のうち論文由来の部分（作成者の名前、人がタスクを書いて一意性を検証した流れ）は、論文本文でもう一度確認する必要があります。

| 観点 | 今日の評価セット | τ²-bench |

| 検証 | 受講生と講師のラベルを比べる（人同士でも割れることを確かめる） | 公開後もレビューと修正が続く（75 件以上の修正、50 件の差し替え） |
| 1 件の形 | 1 問 1 答 | 多ターンの対話。相手も LLM が演じるユーザーで、ツールで状態を変える |

| 繰り返し | 1 回ずつ採点 | pass^k で、同じタスクを何度やっても成功するかを見る |

- 気づき・疑問：
  - 今日の演習では「LLM の採点を信じてよいか」を人のラベルとの一致率で確かめましたが、τ²-bench は採点の大半を **DB の状態の照合（コード）** に寄せて、LLM 採点への依存を減らしています。「コードで判定できる形にタスクを作る」ことが、規模を大きくする条件になっていると感じました。今日の「回の表示」をコードで判定したのと同じ考え方です
  - それでも、正解の DB を作る `actions` を人が書く以上、間違いは混ざります。実際に公開後に 75 件以上の修正が入っていて、10 件を 1 人で作った今日のセットにも同じ種類の誤りがありうると思いました
  - airline の `nl_assertions`（例：「取り消しを断るべき」）は書いてあるのに、`reward_basis` に入っていないので採点には使われていません。「断る」は DB が変わらないことで確かめています。基準を書いても採点に効いているとは限らず、どの基準が実際に点数を決めているかをコードで確かめる必要がありました
  - 疑問：ユーザー役も LLM なので、ユーザー役がタスクの指示どおりにふるまわなかった失敗は、エージェントの失敗と区別できるのか（ユーザー側の誤りをどう数えているのか）
