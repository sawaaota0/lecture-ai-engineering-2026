- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  - `app/retrieval.py` に `add_neighbors()` と `search_with_neighbors()` を追加し、ベクトル検索の結果に**同じ資料内の前後のページの本文**を付けて返すようにしました
    - 前後は `load_pages()` の並び（資料→章→ページ）でたどり、別の資料（`document_id` が違うページ）はまたぎません
    - 同じページは 1 回だけ返します。検索で当たったページは距離（`distance`）付きで優先し、前後のページには `neighbor_of`（どの検索結果の隣か）を付けます
    - 並びは「検索結果 → その前のページ → 後のページ」を検索順に繰り返します
  - `app/config.py` に `RAG_NEIGHBORS`（環境変数 `AIE_RAG_NEIGHBORS`、既定 0）を追加しました。0 なら従来と同じ結果になるので、**同じコードのまま環境変数だけで変更前後を比べられます**

  - `python -m app.retrieval` に `--neighbors N` を追加し、前後ページには「（前後ページ: … の隣）」、検索結果には距離を表示します
  - `tests/test_neighbors.py`：0 なら変わらない／前後が付く／資料をまたがない／重複しない、を API キーなしで確かめるテスト（`uv run pytest` で 21 件すべて合格）

- 改善した例と、残る失敗・制約：
  - 今回の 2 問では、**根拠が増えて回答が良くなった例はなかった**。通常の検索で根拠のページがすでに 5 件の中に入っていたため。質問 2 で p.38（メモリを全部残す問題）が引用されたが、p.38 はもともと検索結果に入っていたページで、前後ページで足したものではない。回答が少し変わったのは、同じ根拠でも入力が変わると生成が揺れるためと考える
  - 不要な情報が増えた例：両方の質問で、検索結果 5 件に対し 6 件の前後ページが足され、入力トークンが約 1.8 倍になった。足したページはどれも引用されず、回答の誤りも増えなかったが、費用だけが増えた
  - 前後ページが効くのは「答えが検索で当たったページの隣に続いていて、隣のページ自体は検索で当たらない」場合だけ。オフラインで確かめた p.39 → p.40 はその例だが、実際の検索語では p.40 も直接当たった
  - 残る制約：今回は 1 問 1 回ずつで、結果は実行ごとに揺れる。離れたページ（p.13 と p.39）は前後ページでは取れない。章の切れ目では話題が変わるが、今は資料の境界でしか止めていない
- 気づき・疑問：

  - 前後ページを付けるかどうかを、検索の距離（当たりの強さ）や同じ章かどうかで決めれば、不要な情報を減らせるのではないか
  - 前後ページを足したとき、モデルが無関係なページを引用しなかったのは、`neighbor_of` で検索結果と区別できたからか、単に本文が質問と関係なかったからか、は今回の実験では分からない
